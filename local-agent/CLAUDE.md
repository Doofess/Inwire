# local-agent/CLAUDE.md

Build and packaging mechanics for the Windows agent service. Loaded only when
working under `local-agent/`; the rules that must never be got wrong (the
three-place version lock, and `dist/`/`public/downloads/` being untracked)
stay in the root CLAUDE.md so they are always in context.

- `pyinstaller local-agent/inwire_agent.spec` builds `local-agent/dist/inwire-agent-windows.exe` — the service host, entry point `service_windows.py`, built with `console=False`. It accepts `install` / `remove` / `start` / `stop` / `debug`; `debug` requires the service to already be `install`ed first (pywin32's `debug` verb checks the SCM registry before running any agent code), so the practical loop is `install` once, then `debug` to run the service body in the foreground for iteration. Note `debug` is a **log-file** diagnostic, not a console one: the exe is built `console=False`, so `sys.stderr` is `None` and nothing appears on screen — watch `%ProgramData%\Inwire\agent.log` instead. `debug` also only takes effect on the frozen exe; run from source, pywin32 spawns a separate `pythonservice.exe` process, so use `python local-agent/agent.py` for source-level iteration.
- `iscc local-agent/installer/setup.iss` (Inno Setup 6.3.0+ — `setup.iss` uses `ArchitecturesInstallIn64BitMode=x64compatible`, which older Inno Setup releases don't support) wraps that into `local-agent/installer/output/Inwire-Agent-Setup.exe`, which downloads Npcap if missing, registers the `InwireAgent` service as LocalSystem/auto-start, and seeds the config. Copy that installer into `public/downloads/` for the web app to serve.
- **Release checklist** (the three downloads in `public/downloads/` are what users get; a source-only bump ships nothing): bump the version in all three places → `python local-agent/test_protocol.py` → `pyinstaller --noconfirm --clean local-agent/inwire_agent.spec` → `iscc local-agent/installer/setup.iss` → copy `local-agent/installer/output/Inwire-Agent-Setup.exe` to `public/downloads/` → install it here and run `python local-agent/verify_protocol.py` against the live service (it checks `state` after every command, `capture_stats` while sniffing, and the error codes). `inwire-agent-windows.exe --version` prints the built version (and `--init-config` seeds `config.json` with a pairing token, which is what the installer calls - the token is minted by Python's `secrets`, not by Inno Setup's clock-seeded `Random`, and `config.json` is locked to SYSTEM and administrators on every agent run because `%ProgramData%` grants `BUILTIN\Users` read by default and a token readable by every local process is not one). The exe is built `console=False`, so both verbs only produce output through a redirect - the installer runs `--init-config` through `cmd /C ... > file` for exactly that reason.
- macOS and Linux install from `unix/install.sh`, which ships **inside** the tarball `scripts/agent/package-unix.ts --build` produces from the real sources. What it replaced were two bootstrap scripts with a copy of `agent.py` pasted into each; the copies stopped being updated around 2.1 and went on being downloaded, speaking a protocol from before the typed one - so the app parsed zero packets and showed the "Update" pill for ever. Nothing embeds a copy now, and an assertion (`scripts/agent/package-unix.ts`) fails if a module the agent imports is missing from the archive. The installer makes a **root-owned virtualenv** (the old scripts ran `pip --user` as the invoking user and then ran the agent as root, which is a different site-packages), registers a systemd unit or a LaunchDaemon, writes a pairing token, and takes an `uninstall` verb.
