# local-agent/CLAUDE.md

Build and packaging mechanics for the capture agent. Loaded when working under
`local-agent/`. The rules that must never be got wrong — the version lock, and
what the pipe's descriptor grants — are repeated in the root `CLAUDE.md` so
they are always in context.

## What the agent is

A Python process that captures raw frames and does nothing else with them. It
reads with `pcap_next_ex` directly, batches records into a binary format, and
hands them to whoever asked. It does not dissect: a record carries no source,
destination, protocol, ports or info (ADR 0010).

**There is a second agent, in `agent-rs/`, and on Windows it is the one that
ships.** The product installer carries the Rust build, not this one's
PyInstaller tree (ADR 0037): its wire format, pipe and capture path are proven
against the app's own client, and its SCM registration was driven as the
installed service. This agent is what macOS and Linux run, and on Windows it is
now built only to compare against (`agent-rs/switch-agent.ps1 -Python`). **Every
behaviour fix still has to land in both**: the shared golden vectors and the
matching kernel-buffer assertions
are what keep them in step, and a fix applied to one and not the other is the
failure mode to watch for. macOS and Linux keep this one regardless.

On **Windows** it runs as the `InwireAgent` LocalSystem service, is installed by
the product's installer, and its only transport is a named pipe. **It is
demand-start** (ADR 0035): the app asks the SCM for it at launch, and the agent
stops itself two watchdog ticks after its last client leaves. On **macOS and
Linux** it installs from a tarball and keeps the WebSocket — and keeps the
pairing token with it, because there is no interactive-user SID to name on a
socket file and deciding who may open one is a genuinely different design.

## The transport, on Windows

`pipe_server.py` serves `\\.\pipe\inwire-agent` with the security descriptor:

```
D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGW;;;IU)
```

- `D:P` — protected, so nothing is inherited.
- `SY`, `BA` — SYSTEM and administrators, full access.
- **`IU`** — the interactive user, read and write. This is the whole point: the
  service is LocalSystem and the app deliberately is not, and the default DACL
  on a pipe a LocalSystem service creates admits SYSTEM and administrators
  **only**, so without this ACE the app could never connect to the service that
  exists to serve it.
- Absent, deliberately: `WD` (everyone), `AN` (anonymous), `NU` (network). A
  named pipe answers over SMB as `\\host\pipe\name` unless the descriptor says
  otherwise. `PIPE_REJECT_REMOTE_CLIENTS` says it a second time.

Because the kernel decides, the agent asks a pipe client for **no** token.
`register` skips it when the connection reports `kernel_authenticated`, so the
pairing question is never asked rather than merely answered.

**The handle is `FILE_FLAG_OVERLAPPED` and every operation carries its own
`OVERLAPPED` with its own event.** Without it, Windows serialises operations on
the handle: the writer thread's `WriteFile` queues behind the reader thread's
blocked `ReadFile` and waits for bytes that are not coming. Measured against
the real client — `hello` and the first reply arrived, everything after did
not. It works on the handshake, which is what anyone tests, and stops on the
traffic, which is what the pipe is for.

Threads rather than `loop.start_serving_pipe`, and not by preference: the
proactor creates its own pipe instances with the creating process's default
DACL, which for a LocalSystem service is exactly the descriptor that locks the
app out.

`pipe_frame.py` is the framing — a `u32` length, a `u8` kind, little-endian —
and its counterpart is `src/services/agentFraming.ts`. Both refuse a declared
length past 8 MB before allocating. Both assert the same hand-written byte
vectors: `test_protocol.py` here, `scripts/agent/pipe-framing.ts` there.

## The version

**The agent has no version of its own. It reports Inwire's.** ADR 0035.

| Where | How it gets there |
|---|---|
| `package.json` | **the source** — the only place a version is authored |
| `agent_version.py` | generated by `npm run sync:version`, committed |
| `agent.py` | `from agent_version import AGENT_VERSION` |
| `agent-rs/Cargo.toml` + `Cargo.lock` | rewritten by `npm run sync:version`, committed — the Rust agent's `hello`, `--version` and VERSIONINFO |
| `src/services/agentProtocol.ts` | `REQUIRED_AGENT_VERSION`, a literal |
| `installer/setup.iss` | `MyAppVersion`, a literal |

`scripts/agent/version.ts` holds every row to `package.json` on every
`npm run check`, and also asserts the two **deletions** — that the shipping
installer declares no `MyAgentVersion` and that `agent.py` declares no literal
of its own, since either one re-added would fork the number again while every
other check kept passing.

**There were six stamps and two scripts covering different subsets.** This table
said "four places, enforced by two things", and before that "three places"; the
split was the problem rather than the count. `test_protocol.py` read only the
**legacy** `.iss`, and it is Python, so `scripts/check.ts` — which discovers
TypeScript — never ran it; a second script read both `.iss` files and
ran unprompted. The shipping installer's stamps agreed with the code by hand.

`test_protocol.py` still checks the half a Python test is right for: that a
running agent reports the product's version, and that the number has not gone
backwards. `version.ts` is the authoritative one, because it runs unprompted.

Any change to the wire protocol bumps the **product**, and it is still an
**ordering** — the left-hand side of `isAgentOutdated` — so it only ever climbs.
An agent left behind by an earlier install would otherwise read as newer than
required, which shows as "not connected" rather than "update your agent". That
ordering is why unifying moved the product from 1.0.0 to **4.0.0** rather than
moving the agent down from 3.9.0: the surviving number has to be at least the
highest either half ever shipped. The floor is compared as numbers rather than
as a string, because `"3.10.0"` sorts before `"3.9.0"` lexically and a string
floor would reject the first version past 3.9 and every one after it.

`local-agent/installer/setup.iss` keeps a **frozen** `MyAgentVersion "3.9.0"`
and `MyAppVersion "1.0.0"`. Nothing builds it; it records what an agent-only
install actually put on a machine, which is what the unified installer reads in
order to remove it. `version.ts` asserts both stay where they are.

## Building

```
pyinstaller local-agent/inwire_agent.spec
```

Output is `local-agent/dist/inwire-agent-windows/` — a **directory**, not a
file. The entry point is `service_windows.py`: the SCM host, and also the
`install` / `remove` / `start` / `stop` / `debug` CLI the installer drives.

### Why `--onedir`

A onefile build extracts its bundled DLLs to `%TEMP%\_MEI<random>` and executes
them from there. That is a textbook malware pattern — Defender's "block
executable files unless they meet a prevalence, age, or trusted list criterion"
ASR rule blocks it outright — and the extracted DLLs are unsigned however well
signed the wrapper is, because signing a wrapper does not sign what the wrapper
writes to disk. It also paid the extraction at every service start, on a
service that starts at boot.

onedir ships the DLLs beside the exe, where they can be signed and where an
administrator can see what is installed.

### VERSIONINFO

Generated inside the spec from `AGENT_VERSION` rather than written out: one more
copy of a version number would sit outside the four-place lock above and would
eventually disagree with it. Before 3.8.0 the exe had none at all — no
company, no product, no version, which is also what an unsigned dropper looks
like in the one dialog anyone checks.

The Rust agent that replaced this build on Windows carries the same strings,
for the same reason: cargo emits no resources, so `scripts/agent/stamp-agent.ts`
writes them after the link, with this build's icon and an `asInvoker` manifest
where this one says `uac_admin=True`.

### The hidden imports, and why each is there

PyInstaller's static analysis does not see them, and this build is
`console=False`, so a module it quietly dropped shows up as a service that will
not start and says nothing about why.

- `agent`, `agent_log`, `config`, `interface_stats`, `logging_setup`,
  `adapters`, `sockets` — our own, imported inside functions or via `sys.path`.
- `packet_batch` — the binary frame format (3.2.0).
- `pipe_frame`, `pipe_server` — the pipe and its framing (3.8.0). The agent's
  **only** transport on Windows, so a dropped one is an app that never
  connects.
- `win32security`, `win32pipe`, `win32file`, `winerror` — the pipe's pywin32
  surface. `win32security` is what builds the security descriptor, which IS the
  access control: drop it and the agent starts, listens on nothing, and says so
  only in a log the app cannot reach because it cannot connect.
- `win32timezone` — the classic pywin32 omission. Imported at runtime by
  `pywintypes`; its absence shows up only as a service that refuses to start.
- `servicemanager`, `win32serviceutil`, `win32service`, `win32event` — the
  service machinery.
- `scapy.layers.all`, `scapy.layers.inet`, `scapy.layers.inet6`,
  `scapy.arch.windows` — scapy loads layers dynamically.

**Excluded:** `websockets`. `agent.py` does not import it on Windows at all,
and shipping a library the product cannot reach inside a signed installer is
not defensible.

### The installer

```
iscc installer/setup.iss
```

That is the **product's** installer, at the repository root — the app and the
agent in one, under its own AppId. It needs `npm run build:agent` and
`npm run pack` to have run first, and **it no longer ships this agent**: the
payload is the Rust exe, installed under this agent's file name so the
service's ImagePath does not move, and an upgrade deletes the `_internal` tree
this build leaves behind.

`local-agent/installer/setup.iss` is the older agent-only installer and is what
a machine with agent 3.x has; the unified one uninstalls it, because it
registers a service by the same name. **Nothing builds it** — it is kept as the
record of what is installed out there, and its version stamps are FROZEN at what
that install actually put on a machine, which `scripts/agent/version.ts`
asserts. The unified installer does not read it: it carries its own copy of the
GUID as `#define StandaloneAgentAppId`.

## Running it by hand

```
python local-agent/agent.py
```

As Administrator or root — raw capture needs elevation on every OS. On Windows
this needs Npcap already installed; the installer normally handles that.

Two things about the frozen exe. `debug` requires the service to be `install`ed
first, because pywin32's `debug` verb checks the SCM registry before running
any agent code — so the loop is `install` once, then `debug`. And `debug` is a
**log-file** diagnostic, not a console one: the exe is built `console=False`,
so `sys.stderr` is `None` and nothing appears on screen. Watch
`%ProgramData%\Inwire\agent.log`.

`--version` produces output only through a redirect, for the same reason — and
it raises a **UAC prompt** when run by hand, because the exe is built
`uac_admin=True`. Harmless from the installer, which is already elevated; it
hangs a command typed at a prompt.

There was a `--init-config` beside it and it is **deleted, and must not come
back**. It minted a pairing token and wrote `config.json` so the installer could
print the token on a finish page. The token does not exist on Windows — the
pipe's descriptor is the authentication — and neither installer has called the
verb since 3.8.0. `service_windows.py` carries the note where the branch was.

## macOS and Linux

One tarball, built from the real sources:

```
npx tsx scripts/agent/package-unix.ts --build
```

It writes to `release-artifacts/`, which is **not** under `public/` — Vite
copies `public/**` into `dist/` verbatim, so an artifact left there is packaged
inside the desktop app. That is how a stale 21 MB installer came to be two
thirds of a 30 MB renderer bundle.

The archive carries its own `install.sh`: a root-owned virtualenv, a systemd
unit or a LaunchDaemon, a pairing token, and an `uninstall` verb. It replaced
two bootstrap scripts that each embedded a copy of `agent.py` frozen around
2.1 — a copy that can go stale will, so there is no copy, and
`scripts/agent/package-unix.ts` fails if a module `agent.py` imports is missing
from the archive.

## Release checklist

A source-only bump ships nothing.

1. Bump `version` in `package.json`, then `npm run sync:version`. That is the
   whole of it — there is one number now (see the table above).
2. `python local-agent/test_protocol.py`, and `npm run check` — the second is
   what covers every stamp, including the shipping installer's.
3. `npm run build:agent -- -Test` — the Rust agent the installer ships: tested,
   built, stamped, then signed, in that order, as
   `agent-rs/dist/inwire-agent-windows.exe`. Set `INWIRE_REQUIRE_SIGNING=1` for
   a release, or a machine with no certificate configured ships it unsigned
   with only a warning.
4. `npm run pack`
5. `iscc installer/setup.iss`, then `npx tsx scripts/agent/built-version.ts` —
   every artifact's version, and the agent's resources, read back.
6. Install it here (elevated), then `npx tsx scripts/electron/agent-live-drive.ts`
   — the real app against the installed service — and a capture on the real
   adapter, frames on screen.

Step 3 was `pyinstaller --noconfirm --clean local-agent/inwire_agent.spec`
until the installer took the Rust agent (ADR 0037); that build is still how this
agent is made for Windows, and nothing ships it.

Step 6 used to be `python local-agent/verify_protocol.py`, which **cannot work
on Windows**: it dials `ws://localhost:8999` with a token and an `Origin`, and
the Windows agent opens no port, wants no token and sees no origin. That script
is the macOS/Linux check and now says so and refuses to run here.

Neither `local-agent/dist/` nor `release-artifacts/` is tracked in git, and
neither is the Rust agent's output. Rebuild rather than editing binaries.

## Logs

`%ProgramData%\Inwire\agent.log`, rotating. When the agent runs as a service
there is no console, so this is the only place to look. The app surfaces it in
Settings → Driver Info, which is also where it says **why** the agent is not
answering — not installed, disabled, stopped, or crash-looping — rather than
one word covering all four.
