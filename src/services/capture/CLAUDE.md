# src/services/capture/CLAUDE.md

The on-disk capture format and the store protocol; loaded when you work under `src/services/capture/`. The store's process, memory ceiling and ports are in `electron/CLAUDE.md`, and `docs/architecture.md` has the data flow.

## Layout

- A capture is a directory named `cap-YYYYMMDD-HHMMSS-xxxx` (`CAPTURE_ID_PATTERN`, `captureDirectory.ts`) holding seven files: `index.iwidx`, `prefix.iwpfx`, `summary.iwsum`, `frames.iwbyt`, `records.iwrec`, `streams.iwdig` and `marks.iwmrk`.
- `records.iwrec` is one deflated block of frame records per chunk (ADR 0049), written before the chunk's index record so recovery covers it unchanged.
- The index is version 3 (`INDEX_VERSION` in `captureIndex.ts`): an 80-byte stride carrying the records' extent and each chunk's segment. Versions 2 and 1 still open and are continued as themselves; a version 1 capture's trees fall back to the replay. Never migrate an old capture in place.
- A chunk that holds a shard's packed rows is version 3 (ADR 0053 phase 6): a container of complete version 2 summaries (the packs, cut by row selection at a chunk boundary), a segment per row, and side sections for overlays and patches, applied at decode in the old order. The prefix block is unchanged. Every other chunk is version 2 byte for byte. The writer's `packNative: false` re-encodes and is the kill switch. An older build opens such a capture and fails the row reads of each version 3 chunk. `scripts/capture/pack-native-equality.ts`.
- A version 2 chunk records each frame's `linkType`. Version 1 still decodes; `RowBlock.linkTypesStored` says whether an absent link type means Ethernet (v2) or not recorded (v1). Imports need it stored: every frame of one carries one adapter label whatever its link type (ADR 0046).
- `streams.iwdig` is the stream digest's snapshot (ADR 0055, `digestCodec.ts`): every row folded into a summary per stream. Format 6 holds five kinds: TCP streams (states, totals, outcome), each TLS session on a TCP stream (its phases, beside the TCP entry, never inside it), UDP flows (a classic DNS flow carries its answer tally) and QUIC connections (totals, outcome, QUIC's phases), and DHCPv4 exchanges keyed by the unsigned `dhcp.id`. Flows are routed by `udpKeyOf`, `quicKeyOf` and `dhcpKeyOf` alone (every UDP row with a `udp.stream` is in its UDP flow, a numbered QUIC datagram is also in its connection, a DHCP row also in its exchange; `inFlow` is the one test), and the snapshot carries the capture's last frame time. Only rows the writer stored are folded: a row held for its bytes when they come, never one sealed as missed, whose slot is a placeholder. **It is a cache, never a source.** The store writes it at `finish` and at close (`trySnapshot` in `captureHost.ts`), and an open trusts it only when it was folded through the capture's newest id; missing, torn, another format or another id, it is folded again from the rows, sliced through the queue like a scan. The file is emptied before that fold starts and never written while one runs or after one dropped rows (`DIGEST_DEFERRED_MAX`), because a partial digest written as whole is a wrong answer the next open would trust. A partial one is sent as `partial` with the digest's answer, and the Statistics note says so. `snapshot()` hands out the digest's own entries and `restore` adopts what it is given: encode at once, and pass `restore` only fresh decode output. A copy either way was seconds at 100k streams, and the format writes 512-entry deflated chunks, because one JSON string of the whole digest passes V8's string limit near 300k streams. One per capture, beside the index, not per segment. `scripts/capture/stream-digest-store.ts`.
- `marks.iwmrk` is the user's packet marks (ADR 0067, `src/services/marks.ts`): JSON `{"v":1,"ids":[...]}`, ids ascending, the `Packet.id` that `frame.number` reads (stable across a reopen, because numbering resumes past the highest stored id). **It is a source, not a cache**: nothing else records what the user marked, so the store writes it whole on every `marks` message (not at close) and empties it for an empty set. A missing, torn or foreign file opens as no marks and never fails the open. `ready` carries the set; a `marks` message naming a capture other than the open one is ignored; `onScan` compiles with `{ marked }` so `frame.marked` answers over disk rows. It may hold ids the ring has expired; they match no row. One per capture, beside the index, never in a segment, never in the pcapng; it goes with the directory, so `planPrune` needs no change. `scripts/capture/marks-store.ts`.
- Writing is `captureWriter.ts` through `chunkCodec.ts`; reading is `captureReader.ts`; addressing `captureIndex.ts`; search `captureScan.ts` and `matchSet.ts`.

## Ring segments (ADR 0052)

- A capture following the agent's ring keeps data in segments: segment 0 is the four data files beside the index, segment *n* a `seg-NNNNNN` directory. Segments are filed by the agent's `capture_boundary` messages (`src/services/pipeline/ringFiling.ts`).
- `segments.ts` is the only place a capture's frames are deleted without the user pressing anything. A segment goes only if it is not segment 0, not the one being written, every frame in it was filed under the capture the agent deleted from, and its newest frame is at or below the deleted file's last sequence number. Oldest first, no gaps.
- Delete by sequence number, never by file: a shed `capture_boundary` would file a whole ring file under the one before it.
- Floor first: the header records the first chunk still held, every lookup below it answers as a hole, ordinals never move. The list, a filter's bitmap and an export start at the floor, they do not renumber.
- `scripts/capture/segment-guard.ts` puts each refusal back wrong. Run it after touching `segments.ts`.

## Deletion

- A capture is deleted only when the user asks (ADR 0012). `planPrune` in `captureDirectory.ts` removes only directories matching `CAPTURE_ID_PATTERN`, never anything else in the folder. `prune([])` on a real directory is a recursive delete of `%LOCALAPPDATA%\Inwire\captures`, and was reachable whenever `loadSessionMeta()` returned nothing. `scripts/capture/prune-guard.ts`.
- Monitoring files (`journal.iwmj`, `rollups.iwmr`) match no capture id and live under a different root, so pruning never reaches them; keep it that way.
- Auto-pause at 99% made the disk buffer unreachable: `planBufferTrim` acts above `1 + BUDGET_SLACK` (0.05). `DISK_RESERVE_BYTES` (2 GiB, `src/services/bufferBudget.ts`) replaced it; `scripts/session/buffer-budget.ts` asserts the inversion.

## File and serialisation traps

- `blockFile.ts` is the seam; `nodeBlockFile.ts` is the real file and the only module here allowed `node:fs`. It must **loop** `readSync` and `writeSync`: a short read on a 5 GB `frames.iwbyt` read as a torn tail and truncated a healthy capture. `scripts/capture/block-file.ts` injects short reads.
- Recovery: a capture whose trailing chunk is incomplete loses that chunk and nothing else (`scripts/capture/recovery-on-disk.ts`).
- `serialQueue.ts` exists because `void handle(msg)` let `append` overtake an async `open` and lost 500 frames. Do not call store handlers unawaited.
- The client's side of the same rule is `portQueue.ts`: every message, request and scan leaves in call order, and in the same turn once the port is up. Posting from a `.then` held an import's whole file in the renderer, because the import's dissection pass yields only between 64 MiB reads, and 2.4M frames ran it out of memory (#19). `scripts/capture/port-queue.ts`.
- Imports bound their RAM tail by `estimateSummaryBytes` against the buffer budget (`residentBytes`), keeping at least the newest frame, and keep raw bytes on the newest `BYTES_RESIDENT_FRAMES` (25,000) only, as the live buffer does, because the budget does not count them: a tail of full-size frames held a 2.7 GB file's bytes, 2.5 GB past the budget (#20) (`scripts/capture/import-tail.ts`); `scripts/electron/import-heap-drive.ts` is the end-to-end gate. Chromium's `usedJSHeapSize` includes ArrayBuffer backing stores (the rows' bytes), which sit outside V8's 4 GB heap limit; the drive prints both.
- A structured clone drops prototypes. A buffered `Packet` carries its 33 commonest fields in a `FieldBlock` class instance, so across the store's process boundary `encodeChunk` threw for every frame: `frames.iwbyt` grew, `index.iwidx` stayed empty, `ordinalOf` answered -1 and the list showed the RAM window as the whole capture.
- `storePacket.ts` (`plainForStore`) flattens at the boundary and folds dense columns back into `fields`. A message is a snapshot: always copy, even when there is nothing to fold, because `prepareBatch` calls `persist` before `absorb` and the `postMessage` serialises a microtask later.
- `scripts/capture/store-protocol.ts` round-trips every appended frame through `v8.serialize` and `deserialize` first; it drives the store's whole message union and opens with "every request answers, even when it fails". `scripts/electron/disk-drive.ts` drives a capture past the RAM budget and asserts the two counts diverge.
- The store compresses with node's `zlib` at level 1 (`electron/store/entry.ts`); the rest of the app reads with `fflate`. `scripts/capture/native-zlib.ts` holds that either reads the other.
- This directory imports no Electron and no `node:*` besides `nodeBlockFile.ts` (`scripts/capture/node-safe.ts`).
- Imports are not capped by memory: `IMPORT_PATCH_WINDOW` (100,000, `src/services/pcapParser.ts`) is how long a frame stays reachable by a patch. `scripts/capture/import-stream.ts` forces it small so frames really leave it.
- Nor by the file's size: the frame walk reads through `src/services/byteWindow.ts`, one `READ_WINDOW_BYTES` (64 MiB) window at a time, because a `File.arrayBuffer()` past about 2 GB is refused with Chromium's "permission problems" error (#20). Every offset the walk passes is an absolute file offset, over numbers, never an int32. A pcapng block type the walk does not act on is skipped from its 8-byte header, unread; an EPB past the frame limit loads only its 28-byte head. `scripts/capture/frame-walk.ts` walks a virtual file over 4 GiB (no allocation) with frames past 2^31 and 2^32, and sweeps window sizes that split records.
- An import awaits between windows, so the renderer runs during it. `src/services/importJob.ts` is the one import in flight, outside the panel so a remounted side bar still sees it; App's capture-changing actions refuse while it runs (`scripts/capture/import-job.ts`, `scripts/session/import-gate.ts`).
